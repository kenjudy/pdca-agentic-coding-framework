## Non-negotiables

From `CLAUDE.md` and the supervision protocol. These override any instinct to move faster:

- **One step, one commit. Stop for human review after each.** Do not batch steps.
- **Every code change starts with a failing test.** No exceptions.
- **A RED must actually be red, and you must run it and see it.** State the expected failure
  before running (called shot). If the actual failure differs from the predicted one — including
  "it passed" — **stop and report**. Do not adjust the test until it fails.
- **Never edit `skill/pdca-framework/references/`.** Build artifacts, gitignored, regenerated by
  `bash skill/build-skill.sh`.
- **Push before you finish.** Work is not complete until `git push` succeeds. Never say "ready to
  push when you are."

## Traps found the hard way

Each of these cost real time in the session that produced this plan.

- **`uv sync` rewrites `skill/uv.lock`** (bumps the revision field and re-resolves). It will show
  up in `git status` as an unrelated modification. Run `git checkout -- skill/uv.lock` before every
  commit. Never include it in a commit for this work.
- **`pytest -k` exits code 5** ("no tests collected") for eval classes. Use the full node id:
  `tests/test_evals.py::TestPrompt3Evals::test_3_scenario[3-all-complete]`.
- **Bash working directory persists between commands** in some harnesses but `cd` inside a
  backgrounded command does not affect later ones. Prefer absolute paths or re-`cd` each time.
- **`skill/eval/results/` is gitignored.** Eval reports are local only. If you need a number to
  survive the session, write it into the plan file.
- **A test you wrote as a RED that comes up green is a finding, not an inconvenience.** Report it,
  label it "green on arrival" in the commit message, and do not reframe it as a RED. The plan's
  test list already marks #4–6 this way. This exact situation arose in the previous cycle and the
  honest handling of it changed the design.
- **Never attribute an eval failure to your change from a single run.** Use
  `bash run-ab-eval.sh` and read the Fisher p-value. A scenario in this suite was measured failing
  3 of 18 runs against a master nobody had edited.

## Steps 8–9 specifically

These are the two steps that were originally reserved for Opus. They are yours now because the
plan supplies the judgment as procedure — use it rather than improvising:

- **Step 8:** apply the plan's triage table row by row. If a failure matches no row, that is an
  **escalation to the human**, not a cue to improvise a fix.
- **The verdict-before-fix rule is absolute:** the triage verdict lands as a text-only commit
  before any commit that edits a signal, scenario, or prompt in response to it. No commit may both
  diagnose and fix the same failure. The cheapest route to green is always to weaken the check, and
  that route would restore the exact defect you are removing.
- **Step 9 authors new scenario text.** Present the rewritten scenario to the human for reading
  before you commit it — a passing gate is not sufficient sign-off for authored content.
